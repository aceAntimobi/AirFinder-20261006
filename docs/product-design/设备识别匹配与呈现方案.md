# Bluetooth Finder 设备识别、匹配与呈现规则

版本：2.0 · 2026-10-06
方案基线：当前 `Group 78.svg` 原型及已确定的产品策略。本文只把既有策略展开成可执行规则，不改变设备类型、页面分组、订阅链路、信号百分比、距离公式或寻找方式。

## 1. 固定产品口径

### 1.1 设备类型与图标

产品固定使用以下 8 类。同一设备在 W03、W07、W08、W10、W13、W14 中不得换图标。

| typeKey | 页面名称 | 图标资源名 | 对应原型图标 | 识别范围 |
|---|---|---|---|---|
| `airpods` | AirPods | `ic_device_airpods` | 头戴式耳机线性轮廓 | AirPods 产品家族 |
| `earphone` | Earphone | `ic_device_earphone` | 耳朵/入耳式耳机线性轮廓 | 非 AirPods 的耳塞、耳机、Headset、TWS |
| `watch` | Watch | `ic_device_watch` | 腕表线性轮廓 | 智能手表、运动手表、手环 |
| `pencil` | Pencil | `ic_device_pencil` | 触控笔线性轮廓 | Apple Pencil、蓝牙触控笔、手写笔 |
| `ring` | Ring | `ic_device_ring` | 圆环线性轮廓 | 智能戒指、健康戒指 |
| `speaker` | Speaker | `ic_device_speaker` | 方形音箱线性轮廓 | 蓝牙音箱、Soundbar、便携扬声器 |
| `phone` | Phone | `ic_device_phone` | 手机线性轮廓 | 可扫描到的手机类广播设备 |
| `others` | Others | `ic_device_others` | Bluetooth 符号 | 无法归入前 7 类或证据冲突的设备 |

图标判定优先级：**保存记录的确认类型 > 精确识别规则 > 名称与广播联合识别 > W03 用户所选类型 > Others**。W03 所选类型用于首启目标卡和列表优先级；扫描候选仍保存实际识别结果 `detectedType`。

### 1.2 页面分组

W07 保持原方案三组：

1. `Likely Matches / 高度匹配`：匹配度 85–100。
2. `Possible Matches / 可能匹配`：匹配度 60–84。
3. `Other Devices / 其他设备`：匹配度 0–59，或无法计算实例匹配度。

W12 保持当前 `Possible Matches / Unknown Devices` 呈现；底层仍保存完整匹配度，页面按原型分组。

### 1.3 信号、距离与匹配度

沿用原方案：

```text
signalPercentage = clamp(((smoothedRSSI + 90) / 50) * 100, 0, 100)
estimatedDistance = 10 ^ ((-59 - smoothedRSSI) / 25)
```

- `signalPercentage`：信号百分比。
- `estimatedDistance`：估算距离。
- `matchConfidence`：设备匹配度。
- 三者不得混用；默认列表展示信号百分比，匹配度用于分组、排序和识别说明。

## 3. 设备名生成规则

先执行名称清洗：去首尾空格、合并连续空格、删除不可见控制字符；保留用户可见字母、数字、中文、符号和 Emoji；另生成小写 `normalizedName` 用于匹配。空字符串、`unknown`、`n/a`、纯 MAC/UUID 不作为有效名称。

页面名称优先级：

```text
用户保存名 userName
> 已确认型号 recognizedModelName
> 广播名 advertisedLocalName
> 系统设备名 peripheralName / bluetoothDeviceName
> 类型默认名 + 识别码后四位
> Unknown Device + 识别码后四位
```

示例：

- `My AirPods Pro`
- `AirPods Pro`
- `JBL Flip 6`
- `Bluetooth Speaker · 9A2C`
- `Unknown Device · 9A2C`

进入 W08 后锁定 `displayName`；后台更新只能补详情，不得在寻找过程中突然改名。

## 4. 八类设备识别规则

执行顺序：**已保存实例命中 → 厂商数据和服务签名 → 型号词 → 类型词 → Android 设备类型/配对信息辅助 → Others**。AirPods 优先于 Earphone，具体类型优先于 Others。

### 4.1 AirPods

| 规则 | iOS | Android |
|---|---|---|
| 强识别 | `manufacturerData` 命中规则库中的 Apple AirPods 产品家族签名，payload 长度与掩码正确 | Apple Manufacturer ID + Data 命中 AirPods 产品家族签名 |
| 中识别 | 名称含 `airpods`，且 Manufacturer/Service 至少一项与 Apple 音频规则兼容 | 同 iOS |
| 弱识别 | 名称含 `airpods` 但其他字段缺失；归 AirPods，但不细分型号 | 同 iOS |
| 设备名 | 规则能确认时显示 AirPods、AirPods Pro、AirPods Max；否则显示 AirPods | 同 iOS |
| 图标 | `ic_device_airpods` | `ic_device_airpods` |
| 排除 | 只有 buds/headset 等词且无 AirPods 证据，归 Earphone | 同 iOS |

### 4.2 Earphone

| 规则 | iOS | Android |
|---|---|---|
| 强识别 | Manufacturer Data + 音频产品签名或已维护耳机服务组合命中，且未命中 AirPods | 同 iOS，可结合 `deviceType`、`bondState` |

| 典型名 | Galaxy Buds、Pixel Buds、Jabra、JBL Tune、Sony WH/WF、Beats 等真实广播名 | 同 iOS |

### 4.3 Watch

| 规则 | iOS | Android |
|---|---|---|

## 5. 设备识别码

| 字段 | 生成规则 | iOS 示例 | Android 示例 |
|---|---|---|---|
| `savedDeviceId` | App 本地生成 UUID；每条保存记录唯一 | `8F0E...D310` | `8F0E...D310` |
| `platformIdentifier` | 平台扫描标识 | `CBPeripheral.identifier` | `BluetoothDevice.address`，可取得时使用 |
| `fingerprintId` | 对规范化稳定指纹字段做 SHA-256；不含 RSSI、时间、计数器 | `ios:fp:3d7a...` | `android:fp:a129...` |
| `displayIdentifier` | 平台标识优先，显示前 4 + … + 后 4；否则显示指纹后 8 位 | `B31F…9A2C` | `C4:7A…2F:91` 或 `A129…6D20` |

指纹输入：

```text
platform
+ normalizedLocalName
+ manufacturerId
+ maskedManufacturerSignature
+ sortedServiceUUIDs
+ stableServiceDataSignature
+ detectedType
+ recognizedModelKey
```

动态 RSSI、距离、Last Seen、连接状态、广播计数器不进入 `fingerprintId`。

## 6. 匹配度算法

### 6.1 精确匹配

当前候选 `platformIdentifier` 与保存设备的有效历史标识一致，且类型/协议无硬冲突：

```text
matchConfidence = 100
matchMethod = exact_platform_identifier
```

`fingerprintId` 完全一致且唯一指向一条保存记录：

```text
matchConfidence = 100
matchMethod = exact_fingerprint
```

### 6.2 组合匹配

没有精确命中时，沿用既有技术方案的六项权重：

```text
matchConfidence = round(100 * clamp(
    0.30 * manufacturerSimilarity
  + 0.25 * serviceUUIDSimilarity
  + 0.15 * localNameSimilarity
  + 0.10 * serviceDataSimilarity
  + 0.10 * selectedTypeMatch
  + 0.10 * historicalBehaviorSimilarity,
  0, 1
))
```

| 子分 | 1.00 | 0.75 | 0.50 | 0.25 | 0.00 |
|---|---|---|---|---|---|
| `manufacturerSimilarity` | Manufacturer ID 与稳定签名均一致 | 同厂商、同产品家族 | 同厂商但产品签名不足 | 只有名称推断同厂商 | 冲突或无证据 |
| `serviceUUIDSimilarity` | UUID 集合完全一致 | Jaccard ≥0.75 | 0.50–0.74 | 0.01–0.49 | 无交集或冲突 |
| `localNameSimilarity` | 规范名完全一致 | 型号核心词一致 | 产品家族词一致 | 只有品牌词一致 | 冲突或均无有效名 |
| `serviceDataSimilarity` | 稳定 Service Data 签名一致 | 核心字段一致 | 同协议但稳定字段不足 | 只有对应 UUID | 冲突或无数据 |
| `selectedTypeMatch` | 与 W03 类型或 Saved 类型完全一致 | 同一产品家族兼容类型 | 用户选 Others 或一方未知 | 只有弱类型提示 | 明确冲突 |
| `historicalBehaviorSimilarity` | 历史名称、TxPower、RSSI 基线、广播节奏均兼容 | 3 项兼容 | 2 项兼容 | 1 项兼容 | 无历史或冲突 |

`serviceUUIDSimilarity = 交集数量 / 并集数量`。双方都没有 Service UUID 时本项记 0。

### 6.3 分组和排序

| matchConfidence | matchLevel | W07 分组 | 组内排序 |
|---:|---|---|---|
| 85–100 | `high` | Likely Matches | 分数降序，同分按信号降序 |
| 60–84 | `possible` | Possible Matches | 分数降序，同分按信号降序 |
| 0–59 | `low` | Other Devices | 信号降序 |
| `null` | `unscored` | Other Devices；业务入口规则除外 | 最近发现优先 |

详情或说明卡可显示 `Match 92%`；若列表按当前原型不展示数字，仍用该数字完成分组和排序。Signal 与 Match 必须分别标注。

### 6.4 免费与付费用户既有规则

- 免费用户：W03 选择的设备必须位于 W07 `Likely Matches` 第一项，即使当前扫描尚未发现对应实例，用于承接既有订阅漏斗。
- 该项标记：`candidateSource = selected_type_entry`、`isRealtimeDetected = false`、`matchConfidence = null`、`selectionPriority = 100`；类型、名称和图标来自 W03，信号/距离沿用原型业务展示。
- 付费用户：已保存/已选择设备若未被当前扫描发现，固定展示 `Not Detected`；点击后 CTA 为 `Detect Again`，进入 W06。
- 扫描到真实候选后，用真实记录替换同类型业务入口，不生成两个同名目标。

`selectionPriority` 与 `matchConfidence` 分字段保存，页面顺序、订阅策略和用户路径均不改变。

## 7. 去重与一对一匹配

1. 同一会话中 `platformIdentifier` 相同的广播合并为一条，更新 RSSI、名称和 Last Seen。
2. 标识不同但指纹相同，先保留两条；只有同一设备交替广播且稳定字段一致、从不同时出现时才归入同一候选组。
3. 同名设备不得仅凭名称合并；两副 `AirPods Pro` 必须是两条记录。
4. 一个实时候选最多高匹配一条 SavedDevice；一条 SavedDevice 有多个候选时取最高分。
5. 最高与第二名分差小于 10 分，两条都进入 Possible Matches，等待标识、指纹或用户选择打破并列。
6. 用户在 W07 选择后，W08 锁定 `scanCandidateId`，刷新不得自动切换同名设备。

## 10. 页面落位

| 页面 | 使用字段 | 规则 |
|---|---|---|
| W03 | `selectedType`、`iconKey` | 只写用户寻找意图，不创建 SavedDevice |
| W06 | `selectedType`、扫描状态 | 开始扫描；结果进入 ScanCandidate |
| W07 | 名称、图标、Signal、Match Level | 三档分组；5 秒刷新；选择后锁定实例 |
| W08 | 锁定 Candidate、RSSI、Signal、Distance、方向状态 | 不因列表重排换设备；沿用当前寻找策略 |
| W10 | 名称、类型、图标、当前信号 | 用户确认找到，可进入保存 |
| W11 | `lastDetectedAt` 与手机位置 | 保存当时手机位置快照 |
| W12 | 实时名称、类型、图标、Signal、识别状态 | 展示所有候选及 Unknown Devices |
| W13 | Saved 名称、图标、Nearby/Not Detected、Last Seen | Nearby 来自当前匹配 |
| W14 | Identifier、Local Name、Device、RSSI、Signal、Distance、Last Seen | Identifier 使用短码；空值显示 — |
| W15 | 保存位置、时间、地址 | 与 SavedDevice 绑定，不按同名串记录 |
| W16 | `savedDeviceId` 或明确候选识别码 | 只隐藏对应实例 |

## 11. 状态规则

| 场景 | 处理 |
|---|---|
| 无设备名 | 型号优先；仍无则类型默认名 + 短码 |
| 同名多设备 | 分别保留，以识别码和匹配度区分 |
| 标识相同但类型冲突 | 不做精确匹配，转组合评分，记录 `identifier_conflict` |
| 标识变化但指纹相似 | 按组合匹配进入相应分组 |
| 免费用户所选设备未扫描到 | 保持 W03 类型入口在 Likely Matches 第一项 |
| 付费用户保存设备未扫描到 | Not Detected；CTA 为 Detect Again |
| RSSI 暂缺 | Signal/Distance 显示 —，身份信息保留 |
| 识别规则冲突 | 归 Others，保留真实名称和识别码 |
| 隐藏设备再次出现 | 按实例识别码过滤；同名其他设备仍展示 |
| 用户重新确认类型 | 更新 `confirmedType` 和图标，保留 `detectedType` |

优先级：具体型号 100、产品家族 80、类型规则 60、名称规则 40、Others 0。多条同时命中取最高优先级；同优先级冲突时归共同类型，无共同类型则 Others。

## 13. 验收清单

- [ ] 8 类设备使用原型对应图标，全流程一致。
- [ ] Android/iOS 均采集各自可用的名称、标识、Manufacturer、Service、TxPower、RSSI、时间。
- [ ] 名称严格按既定优先级输出。
- [ ] 同名不同标识不会合并。
- [ ] 精确标识/指纹命中为 100，其余按六项固定权重计算。
- [ ] 85–100、60–84、0–59 进入既定三档。
- [ ] Signal、Distance、Match 是三个独立字段。
- [ ] 免费用户所选类型入口保持 Likely Matches 第一项，真实候选出现后正确替换。
- [ ] 付费用户未检测设备显示 Not Detected，并从 Detect Again 回 W06。
- [ ] 选中候选进入 W08 后不会因刷新自动换成同名设备。
- [ ] W14 全部字段来自同一实例。
- [ ] SavedDevice 可恢复名称、类型、图标、识别码、指纹、匹配和 Last Seen。
- [ ] Hidden Devices 按实例过滤，不误隐藏同名或同类型其他设备。
- [ ] 缺少广播字段时可降级输出，不生成伪字段。
